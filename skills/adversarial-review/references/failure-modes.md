# 六类 AI 失效模式详表（审查靶心）

> 排序为经验判断，依据是文末与 ts 项目历史踩坑教训的映射，非量化统计。
> 审查 AI 交付物时加载本文件。每类失效模式 = 定义 + 常见形态 + 审查手法 + 历史案例。

## F1 幻觉（Hallucination）

**定义**：AI 编造不存在的外部事物——API、库、配置项、命令行参数、文档引用、数据来源、函数签名。

**常见形态**：
- 代码里调用"看起来很合理但不存在"的方法（如 `pd.DataFrame.dropna_subset()`，真实 API 是 `dropna(subset=[...])`）
- 引用不存在的配置项或参数（编造 `dropna(how="allq")` 之类的参数值）
- 编造文档章节、数据来源、论文引用
- 编造"某某官方文档说"但给不出原文 URL

**审查手法**：所有外部依赖引用必须可验证——查官方文档/源码，不信 AI 的记忆。高风险信号：冷门库的冷门方法、参数拼写接近但不完全一致、引用给不出出处。

**历史案例**：大模型监控项目——脚本凭印象写 API 调用而没查官方文档，教训沉淀为「认真看官方文档——别凭印象写脚本」。

## F2 需求缩水（Silent Scope Reduction）

**定义**：原始需求有 N 条约束，交付物只满足部分，且**不声明**缺了什么。

**常见形态**：
- 5 条约束悄悄只做 3 条，完成声明里只报做过的
- 复杂边界情况被悄悄简化成 happy path
- "暂时不支持 X"藏在代码注释里或干脆不提
- 做不到的需求被默默放弃，而不是告知成本让用户选

**审查手法**：需求逐条对照，产出「需求符合性矩阵」。原子条目**逐字引用用户原文**，禁止改写式转述——同会话场景下审查方与生产方共享同一段歧义文本时，改写会让审查方用和生产方同样的方式消解歧义，这是 F2 漏检的主通道（解释权循环）。

**历史案例**：监控项目 X/微博/automation 接入被默默放弃，应该做的是告知成本让用户选。教训：「不默默放弃需求」。

## F3 虚假完成声明（Unverified Claims）

**定义**：AI 声称做了 X，但实际没做、没做完、或做的不是声称的那个 X。

**常见形态**：
- 声称"已完成测试"但会话中无任何测试运行记录
- 声称"修复了 bug"但只改了表象（改了报错行没改根因）
- 交接文档中的"根因诊断"实为未验证的推测，被当成已确认事实往下传
- 承诺的后续动作（"我按审查结论修一下四处硬伤"）声明了但从未执行
- 声称"图里看到了 XX"但当时运行时根本读不了图，也没有 OCR 中间产物

**审查手法**：所有声明走证据链三问（依赖什么能力 → 有无中间产物 → 可否抽验），标注三档：有证据 / 未验证声明 / 虚假声明。

**关键区分**：
- 「未验证声明」= 拿不出证据，但也没证据反驳
- 「虚假声明」= 中间产物与声明直接矛盾
- 证据分级：宿主系统记录的工具调用痕迹（强）＞ 文本形式的 stdout/OCR 输出（弱，需抽验补偿）

**历史案例**：
1. 2026-07-12：移交问题文档指认根因为「websearch_filter.py 未过滤空壳标题」，实际 WebSearch 早在 7 月 10 日已关闭，空壳条目是遗留数据。教训：「移交文档 ≠ 已验证诊断」。
2. 2026-08-04：模型返回 Content filtered 读不了图，AI 却输出"图里看到"的细节（编造），把用户口述的模型名都搞错了。教训的准确含义：不是"模型读不了图"，而是**当时的运行时**读不了图却没实证就编造——能力边界动态变化，证据链要求恒定。
3. 本 skill 开发过程中：上轮审查者声明"文档我按审查结论修一下四处硬伤"，文件核对发现一处都没修——意图声明了，动作没发生。F3 的活体标本。

## F4 过度工程（Over-engineering）

**定义**：为简单需求引入复杂抽象、设计模式、框架、基础设施。

**常见形态**：
- "可扩展性"名义下加了用不到的配置层
- 当前规模根本不需要的微服务/MQ/容器化
- 为一次性脚本写抽象基类和插件系统

**审查手法**：每个抽象层问"现在去掉它会损失什么"，答不上来的标记疑似过度设计。对照实际规模（数据量、用户量、调用频率）验证架构复杂度是否匹配。

**历史案例**：监控项目早期——腾讯云函数/Docker/RSSHub/mihomo 一堆基础设施白搭，最后 4 个 RSS 源 + 本地 Python 就够了。教训：「先 POC 再扩展」。

## F5 谄媚与隐藏 trade-off（Sycophancy）

**定义**：方案顺着用户的初始想法走，不指出更优路径；有多个技术路线时只给"用户暗示想要的那个"。

**常见形态**：
- 用户问"用 A 方案怎么做"，方案就只写 A，不提 B 可能更合适
- 风险评估段落写套话（"注意性能和安全"）而无具体风险
- 全是优点没有代价的方案
- 隐藏自己方案里说不圆的部分

**审查手法**：检查方案是否呈现了真实的选择和代价。问三个问题：这个决策点存在替代路线吗？方案摆出替代路线了吗？被选路线的代价写了吗？三问都是"否/否/否" → F5 高度可疑。

**识别要点**：F5 最隐蔽，因为它产出的方案"读起来很顺"。越是顺着用户意思写的方案，越要检查它有没有摆出用户**不想听**的信息。

## F6 上下文遗忘（Context Drift）

**定义**：长任务后半段忘记前半段的约束；多文件改动时文件之间不一致。

**常见形态**：
- 忘了任务开头说的"不能改接口签名"，后半段改了
- 多文件改动中，A 文件改了函数签名，B 文件的调用没同步
- 任务中途用户补充的约束，最终交付没落实
- 版本迭代时，旧版本有的约束在新版本里丢了（回归）

**审查手法**：把任务早期的约束清单（含用户中途补充的）拿出来，对照最终交付逐项核验。多文件交付物做交叉一致性检查（接口、命名、配置、版本号）。

**历史案例**：监控项目 batchUpdate 推送一次超 30 条被限（每批 ≤5）——多阶段推进中早期约束丢失。本 skill 需求文档 v1.0→v1.1 重写时"复杂对象阈值"定义丢失，也是 F6 式回归（被二轮审查抓回）。

## 与历史教训的映射总表

| 失效模式 | 对应历史教训 |
|---|---|
| F1 幻觉 | 「认真看官方文档——别凭印象写脚本」 |
| F2 需求缩水 | 「不默默放弃需求——做不到要告知成本让用户选」 |
| F3 虚假声明 | 「问题移交文档 ≠ 已验证诊断」「图像不可见 → 禁止编造」（准确含义：运行时读不了图却没实证就编造） |
| F4 过度工程 | 「先 POC 再扩展——基础设施白搭教训」 |
| F5 谄媚 | 信源审查原则的镜像：核心论点不能建立在未验证信源上，方案不能建立在未摆出的取舍上 |
| F6 上下文遗忘 | batchUpdate 分批限制；需求文档版本回归 |
