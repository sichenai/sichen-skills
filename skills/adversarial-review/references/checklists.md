# 分交付物类型检查清单

> 审查时按交付物类型加载对应清单，D0 三动作（需求符合性矩阵/声明证据核验/幻觉依赖排查）所有类型必做，本清单是 D1-D4 的展开。

## A. AI 写的代码

### D0 交付真实性
- [ ] 需求符合性矩阵：逐字引用需求原文逐条对照
- [ ] "已测试"声明的证据：会话中有无测试运行记录（命令+输出）
- [ ] "已修复"声明的证据：有无 diff/重跑验证
- [ ] 代码引用的 API/库/配置项抽查：查官方文档验证存在性
- [ ] 相对路径 vs 绝对路径（部署环境差异是静默失效高发区）

### D1 正确性
- [ ] 边界条件：空输入、超长输入、非法字符、并发调用
- [ ] 隐含假设：文件存在？目录可写？网络可达？编码统一？
- [ ] 错误处理路径是否真的能走到（还是有 except: pass 之类的黑洞）
- [ ] 逻辑分支覆盖：if 有没有漏 else，循环有没有终止条件

### D2 安全性
- [ ] 输入来源不可信时的注入风险（SQL/命令/路径遍历）
- [ ] 凭证处理：有没有硬编码 token/key（项目红线：凭证不持久化）
- [ ] 数据落盘位置：是否写到项目外/系统目录
- [ ] 依赖安全：引入的库是否冷门/无人维护

### D3 健壮性
- [ ] 外部依赖失效时行为（API 超时、网络断、第三方返回异常结构）
- [ ] 资源：长循环有无内存累积，文件句柄有无关闭
- [ ] 并发/重复运行：有无锁或幂等设计（cron 场景高发）
- [ ] 原子性：写文件是 temp+rename 还是直接覆盖（中断会留下什么）

### D4 现实性
- [ ] 环境假设成立吗：目标机器有这个 Python 版本/系统命令吗
- [ ] 规模匹配：这个数据量/频率需要这个复杂度吗（F4）
- [ ] 一次性脚本还是长期能力，设计与用途匹配吗

## B. AI 写的方案/设计

### D0 交付真实性
- [ ] 方案覆盖了需求的每一条吗（F2 高发：方案只回应了好做的部分）
- [ ] "已验证/已调研"声明的证据
- [ ] 引用的数据/案例/文档存在吗（F1：编造信源）

### D1 正确性（逻辑自洽）
- [ ] 方案内部有无自相矛盾（A 节说的约束 B 节违反）
- [ ] 因果链完整吗：每个"因此"前面的事真的成立吗
- [ ] 数字对得上吗：各处出现的数据/比例/估算一致吗

### D2 安全性（风险识别）
- [ ] 方案识别了真实风险还是写了套话（"注意性能和安全"= 没识别）
- [ ] 信任边界：谁能让方案失效（外部输入、第三方依赖、时间）

### D3 健壮性
- [ ] 失败路径：主路线走不通时的 Plan B 存在吗
- [ ] 回滚：方案落地后发现问题，能退回来吗

### D4 现实性（F5 谄媚重点区）
- [ ] **替代路线摆出来了吗**：决策点上有 B 选项吗
- [ ] **被选路线的代价写了吗**：全是优点的方案必有问题
- [ ] 容量估算给了吗：当前规模 vs 方案复杂度匹配吗（F4）
- [ ] 落地成本诚实吗：有没有低报工作量/运维成本
- [ ] 顺着用户最初想法走的方案，重点检查有没有该说没说的反对意见

## C. AI 写的文档/内容（报告、交接文档、分析文章）

### D0 交付真实性
- [ ] 文档声称"已确认/已验证"的结论有证据吗
- [ ] 诊断类文档：结论是实证的还是推测被当成了结论（移交文档 ≠ 已验证诊断）
- [ ] 引用信源：给得出原文 URL 吗；「援引外媒」类二手信源标注了吗

### D1 正确性
- [ ] 事实核查：数字、日期、名称、因果表述
- [ ] 推理链：从数据到结论的每步都成立吗

### D4 现实性
- [ ] 信源分级：一手/二手/未验证，文中区分了吗
- [ ] 估计值标注"估计"了吗（红线：数据不实=翻车）
- [ ] 置信度如实传达了吗，还是把推测写成了确定

## D. AI 给的建议/答案（选型、诊断、决策支持）

### D0 交付真实性
- [ ] 建议依据验证过吗，还是"听起来合理"
- [ ] 有没有把"我不确定"如实说出来

### D4 现实性（F5 重点区）
- [ ] 建议是在迎合提问的倾向吗（用户问"X 好不好"，回答就顺着夸 X）
- [ ] 反面情况摆了吗：什么场景下这个建议是错的
- [ ] 替代建议给了吗，还是只给了用户想听的那一个
